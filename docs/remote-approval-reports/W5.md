## Agent 可见行为与默认值

initialize 根据真实 clientInfo.name 查代码常量，去空格、忽略 ASCII 大小写；配置可以显式覆盖。名称与命令名不同的实测结果已经纳入保守判断。

| 客户端标识 | 默认可用预算 |
|---|---|
| Claude Code CLI | 180 s |
| Claude Desktop | 50 s |
| Codex / codex-mcp-client | 60 s；显式确认硬超时 ≥190 s 后可用 180 s |
| Gemini CLI | 180 s |
| 明确 Cursor IDE 标识 | 120 s |
| Cursor / Cursor CLI / ACP | 50 s |
| Grok | 180 s |
| Devin 或未知名称（含通用 rmcp） | 50 s |

| MCP 配置 | 默认值与用途 |
|---|---|
| KEYVALET_RUNTIME_BUDGETS | clientInfo.name → 秒数的 JSON 对象 |
| KEYVALET_TOOL_TIMEOUT_SEC | 可选的已确认 server 硬超时；预算最多为其值减 10 s |
| KEYVALET_WAIT_IN_CALL_S | 60；与 helper 策略和当前调用剩余预算取最小值 |
| KEYVALET_WAIT_TOOL_MAX_S | 600；单次 wait 仍服从运行时预算，max_wait_s 是 5–600 的可选整数 |
| KEYVALET_PROGRESS_INTERVAL_S | 15；与 helper 间隔协商，只有带 progressToken 才发 notifications/progress |

原 UNLOCK_TIMEOUT / REQUEST_TIMEOUT / PROXY_REQUEST_TIMEOUT 不再固定为 180 / 60 / 200 s。协商耗时计入调用预算，progress 覆盖协商与使用阶段，message 含已等待秒数；无 token 不伪造进度。明确 timeout cancellation 记录 client_timeout_observed，并把该 MCP 实例预算降到 50 s，重启重新查表；普通主动取消不降级。进程遭 SIGKILL 后由 helper 的未完成 wait 断连审计补充观测，不能仅凭断连就判定为运行时超时。

`credential_wait_approval` 按附录 E 提供 schema。描述与 next_steps 明确：批准后直接返回原请求结果，不要重复原请求；helper 重启丢失原操作时，approved_retry_required 才允许同参数、同 approval_id 重试一次。使用类工具支持可选 approval_id。

A.8 的 ok、approval_pending、still_pending、approval_denied、approval_expired、no_approver、approved_retry_required、already_consumed 全部是 isError=false 的正常工具结果，经 kv-i18n 输出中英文。超时、未决定、渠道不可用都不冒充拒绝。`credential_status.remote_approval` 只投影 approval_id / summary / expires_at 等状态信息，不把完整请求或执行结果交给模型。

声明 experimental["claude/channel"]，批准到达时发送 notifications/claude/channel，含 content 与 meta.approval_id；helper 的非消费型、会话定向 resolved 通知支持空闲 MCP 会话。推送不领取结果。CI 已验证 server 能正确发出通知，真实 Claude idle session 的唤醒仍受下文的认证／功能开放限制。

Stop 支持 Claude Code / Devin / Codex 的 block、Cursor 的 followup_message、Gemini AfterAgent 的 deny schema。Unix 使用 getppid 对应的系统 parent_id，Windows 使用认证 pipe 的真实 parent PID。无 pending 时无输出、不增加计数；已有过期或计数耗尽的 pending 输出空对象放行。stop_hook_active / loop_count 提前放行，remote.pending.stop_block 的原子结果为计数权威，每个 approval 最多阻止三次。原 PreToolUse / UserPromptSubmit 行为保留。

网关和透明代理挂连接到 min(http_wait_s, client_timeout_hint_s − 60 s)，默认 http_wait_s=540、未知主机 55 s；内核 TCP idle / interval 为 20 s，不发送应用层心跳。等待耗尽返回 429、Retry-After: 30、X-KeyValet-Approval: pending; id=…，JSON 为 `{error:{type:"keyvalet_approval_pending",approval_id}}`。等待中批准继续正常响应，已执行的 helper HTTP 响应直接返回、不再次 POST。keyvalet run 的包装进程与子进程共享 stderr，开始等待时增加一行设备提示。

## 生产接线与 W1–W5 交界

| 交界／此前缺口 | 当前实现与证据 |
|---|---|
| W1 → W4 身份／目录 bootstrap | 独立 metadata master 与加密元数据库保存账号、身份和目录 mirror；revision / CAS / tombstone 检查回滚。setup-remote 走受信 CLI、owner 与显式确认；软件模式必须显式 --software，原生硬件失败不自动降级。真实加密存储／软件设备 key 重开、CA 重开和 mirror 回滚由 production 测试验证 |
| W2 ↔ W3 relay / queue | 相同完整密文重试幂等，不同内容同标识冲突；队列满时已有信封重试不新增、不重复投递；typed ack、密文绑定 receipt、终态无效信封审计后 ack；去重前限制原始 batch |
| W3 ↔ W4 helper IPC | 身份查询、relay 子协议、spooled / accepted / inspect receipt、half-frame 保留、冷连接显式订阅；EOF 取消等待但保留 pending，不执行、不消费、不写拒绝 |
| W4 生产 runner → kv-core | 认证后 lease 绑定 UID、真实 PID、进程启动时间和可执行文件摘要，凭证版本／配置／完整请求再校验；仅保守地将 GET / HEAD / TOTP 作为 T1，其余使用 T2、管理 T3 拒绝。批准执行复用 kv-core::dispatch_approved 和同一只读凭证快照，原 vault 关闭、进程替换或 lease 到期即失效 |
| W4 → W5 wait / Stop / UI | helper 返回策略；runtime_budget_s 是提示，不是授权。transport 控制字段不进原操作摘要，purpose / frontend 等实际语义进完整绑定；OS caller、agent PID、一次性领取、Stop 原子三次计数、取消审计与非消费通知均有联合回归 |
| W4 → gateway / CLI | 生产 ApprovalProvider 已连接认证后的 root 网关；相同完整请求的并发 SDK 重试合并一个 pending ticket，过期／终态删除缓存。HTTP 只由网关发送，helper 发一次性 permit；method / URL / 过滤后的 headers / 原始 body digest 与长度绑定 |
| HTTPS CONNECT / keyvalet run | loopback、会话 token、显式 DNS host、64 个连接槽；绑定 host 做 TLS 拦截，未绑定 CONNECT 保持字节透明。CA 私钥只在加密 helper 元数据，CLI 只持内存叶子私钥；CSR 的签名／P-256／唯一 DNS SAN／非 CA 条件都校验。私有 CA 文件、SDK 环境与降权子进程已接入口 |
| 跨 MCP 进程恢复 | kv-ipc FrontendContinuation 只接受 tool / op / 有限 formatter options，拒绝未知字段、控制字符和超大值，不含原 body 或秘密。helper 保存且绑定它；新 MCP 进程恢复十类原工具格式化，包括 XOAUTH2、export_file、gateway、IMAP、Graph。文件生命周期按结果到期和连接 generation 清理；缺少可信上下文时不返回中间秘密 |
| Windows caller / worker | 普通 MCP 用 OS parent PID，worker 保留原 agent 进程身份，受信 CLI owner 用自身 PID；Stop 复用认证服务 pipe。cross-target clippy 覆盖相关接线，原生 Windows 运行另列限制 |

联合回归 `kv-relay-client::tests::interfaces::w1_to_w5_real_protocol_approval_executes_once_and_mcp_consumes_once` 验证 W1 key → W2 HTTP / WS → W3 两端 relay client → W4 两端 helper → W5 MCP wait：真实 HPKE 和签名，执行计数 1，第二次领取 already_consumed，两端 spool 排空。该测试注入 OS 身份、presence 和执行 runner；生产执行补由真实 encrypted vault / kv-core / root gateway 回归验证，不将注入式联合测试称为已安装硬件产品验收。

新增 `a_signed_remote_decision_releases_the_real_gateway_binary_request_once` 用真实签名审批决定、ProductionRunner / Provider、加密 vault 和真实 TCP 上下游：批准前不发送；批准后按原 POST、原二进制 body `[0,255,13,10]` 和正确凭证注入发送一次，返回原响应；第二次许可 already_consumed。另测并发 SDK 重试只建一个 ticket、终态／过期缓存清理、PID start 替换撤销 lease，以及本地 timeout / unavailable 继续 pending 而非 denied。

## Review 后直接修复的事项

- 请求绑定：批准检查和实际核心／网关执行使用同一只读凭证快照，关闭原 vault 撤销所有快照；批准等待期间编辑凭证不会使用替换后的秘密。
- HTTP 语义：审批路径拒绝 GET / HEAD body 和重复的单值协议 headers，在创建审批或发送上游之前返回错误；SDK x-stainless-retry-count 不进入审批绑定或实际转发。二进制 body 按原字节摘要，未做有损 UTF-8 转换。
- 等待与通知：协商时间、轮询和清理计时都受剩余预算；跨阶段 progress 不漏 tick / 不重复。取消协商不发起使用，通知与缓存次序避免唤醒后找不到原结果。
- 单次领取与恢复：缓存和待处理上下文有容量／到期限制；所有秘密在丢弃时擦除。helper 重启的 retry 要求相同完整绑定；新 MCP 进程按受限元数据恢复后处理，缺少 export_file 上下文不暴露原值。
- 生产缓存与进程：并发创建审批 single-flight；清理终态／过期 ticket 和失效 session alias；可执行文件摘要流式计算，避免将约 200 MiB 的真实运行时误判为超过旧的 128 MiB 限额。
- timeout：旧原生确认接口返回字符串时，将 timeout / unavailable 显式分类；只有明确的 typed local_approval_denied 才写拒绝。
- 连接生命周期：监听器收到 stop 后退出 accept；TLS / 拨号失败关闭升级连接；双向 EOF 后回收连接名额。修正拨号失败假后端的 unwrap，避免 detached task panic 让连接关闭断言误通过。旧端口是否可重连不再作为关闭证据，因为并发测试可能复用已释放端口；仍检查原连接 EOF、监听任务完成和 vault 引用释放。
- Windows / IPC：修复非 Copy SID 在重建网关时被移动、测试 import 的平台条件；CLI 帧大小、关联 ID、32 个并发上限、断连和通知混排均有回归。

### 三分钟审批验收

真实 Claude Code CLI 2.1.282 + 实际 Rust kv-mcp + 附录 C 假 helper，模型侧由本地合成 Messages API 驱动（真实 stdio MCP 客户端仍是 Claude CLI）：批准延迟 180 s，200 s 预算时原 credential_http_request 一次直接返回 HTTP 200；50 s 预算时原请求返回 approval_pending，三次 wait 最终取得原 HTTP 200，没有再次调用使用工具。本轮 kv-mcp 复测的整回合分别为 180.906 / 180.917 s。选择 200 s 是为了让 180 s 批准处在预算内，避免恰好 180 s 边界的调度竞态；wait_in_call 同样显式为 200 s，V1 的默认仍是 60 s。

最终证据为 `final-acceptance/claude-local-approval-{200,50}/{stdout.log,model.jsonl,run.json}` 和 `final-acceptance/acceptance-summary.json`；逐条检查工具结果和调用序列，两组原 HTTP 工具各调用一次，续等次数分别为 0 / 3。审批执行计数的严格断言由 CI 测试给出。账号联网与空闲 channels 验收仍未通过；没有把本地合成模型接口称为有效 Claude 账号或托管模型实测。

补充在真实 `codex exec` 上运行**实际 Rust kv-mcp 服务器 + 附录 C 假 helper**，批准延迟 180 s：

| 配置 | 实际结果 |
|---|---|
| runtime override 200 s、wait_in_call 200 s、Codex tool_timeout_sec 300 | credential_http_request 调用一次，预算内直接得到原 HTTP 200 与合成 body |
| runtime override 50 s、wait_in_call 200 s、Codex tool_timeout_sec 300 | 原调用返回 approval_pending；三次 credential_wait_approval 得到 still_pending、still_pending、原 HTTP 200；原使用工具没有重发 |

### §6.9.3 修订建议

1. Codex 0.162.1 的 TUI 与 exec 都完成了无进度的 240 s 调用；本次没有配置延长四分钟探针的 tool_timeout_sec。这只能给出 ≥240 s 的下界，不能据此证明确切 300 s 默认值或所有旧版本都安全。保留兼容旧版本的 60 s 默认预算；部署确认超时后采用 180 s。
2. Codex 的 Stop 能力行补充：本机版本的 exec 也实测触发 Stop 并遵循 block/active 循环保护，不再限定为 TUI。[官方 hook 文档](https://learn.chatgpt.com/docs/hooks)作为配置来源，实测字段另列。
3. Cursor CLI 保留不可配置的约 60 s 硬限；补充它未提供 progressToken，无法执行合法的 progress 组，因此不能宣称 progress 无效。`Cursor` 名称不能直接按 IDE 120 s 查表；默认 50 s，IDE 需明确标识或配置。
4. Devin 标注此次版本至少可阻塞 240 s、提供 token、Stop 可继续回合；仍保留未确认环境 50 s。其 clientInfo 为通用 SDK 名 `rmcp`，不能全局把 rmcp 归为 Devin 或提高预算。
5. Claude CLI 补充本地模型接口下 ≥240 s 的生命周期证据、progressToken 与 Stop 输入字段；此测试不证明 28 h 或 30 min 空闲边界。Desktop、Gemini、Cursor IDE、Grok 原外部事实保留为文档证据，不用未进入调用的结果修订其上限。Claude channels 的空闲唤醒仍需可用 Claude 会话。Grok 6000 s 仍为[官方配置文档](https://docs.x.ai/build/settings)证据，未做此次工具阻塞验证。
6. channels 实测清单明确要求交互式会话；[官方 channels reference](https://code.claude.com/docs/en/channels-reference)说明开发 flag 在 `-p`／Agent SDK 下被忽略。最终重跑真实交互式 TTY，使用 `--dangerously-load-development-channels server:keyvalet`：MCP 已 initialize，但 UI 明确显示 “Channels are not currently available”，未调用 arm_channel，不能验证空闲唤醒。证据为 `interactive-retest-4/claude-local-channel/` 和 `interactive-retest-4/run.json`。该隔离探针使用合成本地 Messages 端点；这不证明所有 Console API key 模式不支持 channels。[官方 channels 文档](https://code.claude.com/docs/en/channels)列出 claude.ai / Console API key 认证、组织开关和分批开放条件。现有联网 Claude 登录复测则在进入工具前 OAuth 刷新失败。
