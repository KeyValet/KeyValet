# W7 — kv-cli remote approval commands

Date: 2026-10-12. Scope: `rust/crates/kv-cli/` and this requested report. The shared main working tree was used; no git state-changing commands were executed. Existing changes from other workflows were preserved. No dependency was added by W7.

## Implementation

The CLI now exposes the commands in architecture §9.3, notification policy from §6.10.4, and the remote grant revocation example in product J-R3b. Every new command accepts `--json`; help and argument validation work before installation trust checks. Actual operations still authenticate the installed CLI and helper. The CLI sends public intents and renders metadata. The helper owns private keys, signing, authentication level selection, and authorization enforcement.

Implemented command families:

| Command | Behavior / helper operations |
| --- | --- |
| `relay install` | Substitutes the W2 systemd/nginx assets, writes them atomically, sets the public relay URL, and prints the three Cloudflare steps. Supports `--listen`, `--data`, `--public-url`, and an optional staging `--root`. |
| `relay status` | Calls `/v1/health`; accepts an optional `--public-url`, otherwise reads the client configuration. |
| `relay set-url <URL>` | Atomically changes `relay_url`, preserving existing public `device_id` and `account_id`. |
| `pair --new` / `pair <URI>` | Calls `remote.pair.start` / `remote.pair.complete`, displays the URI and six-digit SAS, polls `remote.status` while waiting for SAS, asks for terminal `y/N`, and calls `remote.pair.confirm`. |
| `devices list / revoke <id> / rename <id> <label>` | Calls `remote.devices.list/revoke/rename`. |
| `approvals [--watch] [--on-approve <cmd>]` | Calls `remote.pending.list`; renders pending requests and recent explicit decisions. Watch emits changes once and executes the hook once for an observed request with an explicit Allow decision. |
| `approve <id> [--scope …]` / `deny <id> [--reason …]` | Calls `remote.decide`; forwards scope choice and optional denial reason. The helper chooses Quick/Strong. |
| `grant … / list / revoke <jti> / revoke-all` | Full §7.1 issue arguments; calls `remote.grant.issue/list/revoke`. Revoke-all sends a `revoke_all_grants` Directive to each current executor. |
| `remote <device> mode` | Issues `set_mode`. |
| `remote <device> allow` | Issues a T1 Grant with credential/device/global scope and optional host, method, path, agent, and expiration restrictions; supports `--all` and `--standing`. |
| `remote <device> unattended --include-sensitive --until …` | Requests a T2 Grant through the two-stage helper preparation and terminal label confirmation described below. |
| `remote <device> lock / unlock-ttl / class / label / notify` | Issues the corresponding typed Directive, including `notify` policy. |
| `remote <device> status / pending / grants / audit --since …` | Issues the corresponding query Directive; parses relative or RFC3339 audit boundaries. |
| `remote <device> grant revoke <jti> / revoke-all` | Issues `revoke_grant` / `revoke_all_grants`. |
| `status [--summary]` | Adds relay status, paired device count, pending count, active grant count, and an unattended indicator. Both local status and remote query results highlight unattended in red on a terminal. |

Device resolution prefers an exact active ID, then a unique active label. Duplicate labels return exit 2 and require an ID. `*` selects active devices with the Execute capability. Wildcard Directives fan out to concrete device IDs; a partial failure reports the IDs already completed.

`grant …` carries `source: "preauthorization"`; `remote … allow/unattended` carries `source: "settings"`. This preserves the distinction between §7.1 preauthorization and a short §7.4 Grant even when their scopes are equal. It is a helper input outside the signed Grant, and the helper must enforce the relevant minimum authentication itself.

Unattended preparation first asks the helper to perform Strong and return a short-lived confirmation token, the bound executor ID, and its current label. Preparation must not sign, install, or send a Grant. The CLI then requires the exact label from the controlling terminal, with no `--yes`, piped-stdin, or JSON bypass. A second issue request carries the same intent plus the label and token. For `*`, all current executor labels are confirmed before any final issue request; a cancelled confirmation therefore sends no Grant. The signed Grant never contains the preparation token or command source.

Hooks receive exactly the approval ID and observed summary as arguments. IDs and summaries are not interpolated into shell source. Historical approvals, denial, disappearance, and repeated history do not trigger a hook. Unix hooks drop to the invoking owner before execution; Windows hooks require a non-elevated user session. Hook output cannot corrupt the CLI's JSON stdout.

## JSON and exit behavior

Ordinary success is one tagged JSON object. Pairing and watch use one complete object per update (JSON Lines). Ordinary commands deserialize as `JsonSuccess`/`Success` and the corresponding W0 payload types where available. For example:

```json
{"ok":true,"command":"decision","result":{"approval_id":"approval_test","decision":"allow","sent":true}}
```

Errors have `ok: false` and `{ code, message }`. Partial wildcard failure additionally has `error.completed_devices`. Human messages go through kv-i18n; arbitrary helper error text is not printed. JSON retains lossless metadata strings, while human output escapes control characters.

| Exit | Mapping |
| --- | --- |
| 0 | Success, including a clean Unix watch interruption. |
| 2 | Invalid arguments, unknown target, ambiguous label. |
| 3 | Executor/helper rejection, insufficient authorization, invalid trusted response, or local operation failure. |
| 4 | Timeout or expiration, including pairing and Directive result timeout. |
| 5 | Relay/helper unreachable; health errors, including malformed/oversized health replies. |
| 6 | Strong cancelled, missing secondary confirmation, or terminal confirmation cancelled. |

For legacy compatibility, local `status` still succeeds when the remote helper is unavailable: it reports `remote: null`, `paired_devices_n: null`, and a structured `remote_error`. It never presents unknown unattended status as `false`. Explicit remote operations return exit 5 when unavailable.

## Deviations and integration requests

### W7-IPC-01 — typed CLI Grant/Directive intents and two-stage T2 confirmation

Current W0 `Unsigned<Grant>` and `Unsigned<Directive>` remove only `sig`, while still requiring issuer/algorithm/identifier/nonce fields. Current W4 handlers deserialize those full unsigned objects. Filling those fields in the CLI would conflict with W7's key ownership and authorization boundary. Add typed public intent projections in kv-ipc and accept them on the existing `remote.grant.issue` and `remote.directive.issue` operations. W7 currently sends only requested scope/action/recipient/expiration, and the command source described above; the helper must choose its own issuer, algorithm, identifier, nonce, signature, and Directive expiration.

For `max_tier=T2`, extend `remote.grant.issue` with a preparation result:

```json
{"confirmation_token":"opaque-one-use-token","expires_at":1791648120,"device_id":"dev_srv","label":"srv"}
```

The helper must authenticate Strong before returning it, bind it to the exact draft, recipient, current label, and authenticated caller, expire it within 120 seconds, and consume it once. It must reject a mismatched or missing token/label on final issuance and must not issue on preparation. Ordinary successful issuance keeps `{ grant }`. A `source` value cannot lower the helper's required level for standing, broad, or T2 authorization; §7.1 preauthorization always requires Strong. These proposed wire shapes need W0/W4 integration before the issue commands work with the real helper.

### W7-IPC-02 — helper-selected Decide authentication, reason, and scope anchor

W7 sends `{ approval_id, decision, scope, scope_option, reason? }` and omits `level`. Extend the CLI-facing Decide projection so the helper selects authentication and validates the choice against the request's offered scope options. For remembered scopes, anchor `scope.until` to the helper's signed `issued_at`, using `scope_option`, rather than trusting the CLI clock's provisional timestamp. The optional denial reason must be reflected in the signed decision. Success remains `{ sent: true }`.

### W7-IPC-03 — joining CLI pairing and helper-owned confirmation

Joining sends `remote.pair.complete { uri }`; the helper must parse the relay/token, generate its own keys, register/join, and return or publish SAS. Initiation returns `{ uri, sas, expires_at }`, allowing an empty SAS while waiting. `remote.status.pairing` should expose SAS, expiry/state, or a structured pairing error. Confirmation sends `{ sas, confirmed: true }`; the helper applies executor terminal confirmation or approver Strong according to its role. Current W4 `pair_complete` accepts a peer PairAccept and PairConfirm expects signing fields, so these paths need typed CLI projections too.

No Appendix C pairing abort operation exists. A local rejected confirmation stops the CLI and leaves the helper attempt to expire; add an explicit owner-only abort path if immediate cleanup is required.

### W7-IPC-04 — approval-side pending summaries and recent decisions

`remote.pending.list` on an approver must include incoming approval summaries and bounded recent explicit decisions, not just local executor requests. W7 expects `{ pending: [...], recent?: [...] }`, with each recent entry carrying `approval_id`, `decision`, and an optional summary. It accepts both a top-level summary and `operation.summary`. Keep the result limited to public approval metadata and provide bounded retention or a cursor for long-lived watches. A missing `recent` field renders correctly but cannot trigger `--on-approve`. Current W4 local pending summaries alone do not satisfy this watch contract.

### W7-IPC-05 — issued Grant ledger and revocation propagation

`remote.grant.list` needs the correct local/issued ledger, including remaining budget, expiration, and recent-use metadata. `remote.grant.revoke` must propagate revocation to the affected executor(s) when invoked on an approver. W7 does not infer recipients or silently substitute a new IPC operation; current helper-local revocation requires W4 integration.

### W7-W9-01 — relay-client bootstrap and deployment ownership

On a fresh installation, `relay set-url` writes only the public URL because the CLI has no legitimate account/device identity to invent. Pairing/bootstrap must persist helper-returned public `device_id` and `account_id` before starting W3, whose configuration requires both fields. Reconcile the shared `setup-remote <account-id>` bootstrap with J-R1's anonymous-account/recovery-code flow; requiring the user to supply an account ID is not that product flow. Recovery secrets and key creation remain helper responsibilities.

`relay install` writes a distinct `keyvalet-relay-server.service`, avoiding W3's `keyvalet-relay.service` client unit. W9 must create the dedicated W2 server account, install the binary at the W2 template's `/usr/local/lib/keyvalet/kv-server` path (or reconcile that asset path), create/chown custom data paths, manage Origin CA files, and reload/start systemd/nginx. Existing client configuration permissions/ownership must allow the W3 service to read the public binding.

On Linux, the default install root is `/`; on macOS/Windows it is a staging `relay-install` directory beside client configuration. `--root` can select an explicit staging root. `--data` always names an absolute Linux deployment path; public installation URLs must be HTTPS origins on port 443 without a path. The CLI writes templates but does not install packages, create service users, issue certificates, or start services; those are W9's installation duties. No Tailscale, Caddy, Let's Encrypt, or self-signed path was added.

HTTPS health checks use the system curl executable with normal certificate validation, disabled curl configuration, an empty environment, short timeouts, and bounded stdout. HTTP is accepted only for a numeric loopback IP and uses the built-in bounded transport. W9 must retain curl in CLI deployment environments unless a shared HTTPS transport is made available without adding a W7 dependency. Tests use fake health and loopback HTTP and do not require curl.

No suitable QR rendering dependency already exists in the workspace. As authorized, W7 prints the validated `kv-pair://` URI and defers QR rendering. W0 should select and lock a terminal QR renderer meeting the project's release-age requirement; then W7 can add the renderer without private-key or pairing-policy changes. No dependency was added or approved implicitly by this report.

### Remaining command-shape decisions

- Device rename is `devices rename <id> <label>`. `class` accepts a class name, `--exp`, and optional credential/host matchers. `unlock-ttl` accepts numeric hours or a duration. These fill the unspecified `…` entries with W0 Directive argument shapes.
- `remote … notify` is included even though §9.3 omits it, because §6.10.4 explicitly specifies it. Remote grant revoke is included for product J-R3b.
- Wildcard T1 Grants retain `aud="*"` and warn about future executors. Wildcard T2 Grants target current executors individually because W0's single `confirm` string cannot safely confirm multiple executor labels. Future executors are excluded from that T2 batch; a true global T2 confirmation shape needs a contract/product decision.
- The task requires unattended `--until`; permanent T2 issuance is rejected, despite §7.6 describing a separately confirmed permanent option. `remote … allow --standing` remains available for T1.
- Plain positive numeric `approve <pid>` on Linux keeps the existing polkit path. Remote approval IDs can be numeric when `--json` or a remote scope option disambiguates the command.
- Windows/Linux received cross-target compile/lint checks only. Hardware authentication, actual service installation, public TLS, nginx operation, and Cloudflare edge behavior were not exercised by W7 on this macOS host. Deployment-template contents were tested from the W2 repository assets.
