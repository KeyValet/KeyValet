## Review findings and fixes

- A malformed native child reply (null, array, scalar or `ok: false`) could reach object indexing and panic, or return untrusted child error text. `agent::ui_reply` now validates the object, restores the authenticated request id and returns a static error on failure. Regression cases include both u64 limits and malformed output.
- A rejected wake batch could consume popup slots for requests never delivered. Queue changes commit only after the complete batch validates. Unknown delivery modes fail closed for both backlog and ordinary requests. Tests verify that a failed batch leaves the five-popup budget available.
- Typed executor-label confirmation relied on earlier control state. Both native callbacks recheck the exact label at acceptance; Allow starts disabled. Timeout, failed UI, Escape and close preserve pending state, including the macOS timeout/deny race. Tests exercise the portable policy for every button and failure mode.
- Binary replies were sliced before validating the reported length. Both adapters validate nonzero length, the protocol maximum and the fixed buffer before writing the header. Tests cover invalid lengths, truncated input, binary/newline boundaries and write/flush failures.
- The macOS registration exchange could block indefinitely; it now has bounded read/write timeouts and clears the read timeout after registration. The Windows presence worker handles join failure without panicking. Ephemeral-socket tests exercise registration and helper peer authentication without an installed daemon.
- Dialog reply decoding, framed input, retry routing and stdio processing now have injectable IO/UI boundaries. Fake providers, dialogs, transports and signals exercise error paths without root, GUI, biometric prompts or installed KeyValet. The approval clock is sampled after the dialog through a borrowed `Fn` callback; it is not frozen before a prompt.

## Contract decisions and W1 interfaces

- Appendix C overrides §6.4: decide/grant/directive flows submit unsigned inputs to the authenticated helper. The helper binds the stored request, canonicalizes with W0, and signs through the W1 Quick/Strong provider. Authentication booleans never substitute for signatures.
- §4 / A.7: `PairingFlow` signs the six ASCII SAS digits with the injected Strong `kv_ipc::remote::DeviceKeyProvider`, verifies the pinned AK_s JWK, then calls `remote.pair.confirm`. SAS computation and peer/account binding remain W0/helper responsibilities.
- `KeyAuthorization` performs a fresh key-bound signature and verifies the pinned AK_s. `ObjectCrypto` injects W0 JCS/verification without a new dependency. ES256/RS256 are selected from the recorded AK_q/AK_s alg. Hardware errors fail closed.
- Current injection: ordinary tests use fake dialogs/transports/providers; the compatibility suite injects actual W0 `SoftwareDeviceKey` with fixed W0 P-256/RSA keys. Software is explicit and confined to tests. GUI previews cancel and never sign/contact a helper. Production callers supply W1 providers and the W0 crypto adapter.
- §5 / §6.3 / §9.2: creation time, clock offset, backlog count and unattended status are separate authenticated display context; purpose/extensions/relay timestamps cannot supply them. Offsets greater than 60 seconds in absolute value are highlighted.
- A.2 / §7.6: reject malformed/unknown authority values, duplicate/unoffered scopes and T2 widening. Unknown descriptive protection displays `unknown`. Preserve original JSON; pass only public display fields to native UI. Decisions revalidate original authority rather than mutable presentation fields.
- §7.4 / A.3: per-use/session/standing scopes use `until = 0`; remember adds the selected duration to the decision clock. Session lifetime/final issuance remain executor-owned. `grant_for_scope` is a preview and returns no Grant for per-use, including T2.
- §3.1 / §6.4 / W0 validation: unlock/admin, T2, minimum-Strong and standing selections require Strong, including signed denials. Reasons are optional, single-line, at most 512 characters.
- §7.5 / A.5: tightening/queries/grant revocations/locks/notification use Quick; relaxed modes, increased TTL, changed class matches, rename/device revocation use Strong. Missing authenticated comparison state fails closed. Revocation uses dedicated typed-label copy and removes caller-supplied confirmation.
- §7.6 / A.4: settings Grants always require Strong. T2 exists only in that flow, defaults to seven days, and requires Strong followed by exact executor-label entry. Standing T2 asks for a second confirmation. Global T2 fails closed pending a multiple-executor confirmation contract.
- Product §6.1 / §7.4: global T0/T1 requires a warning about future paired executors followed by Strong. Global/unattended choices are never added to popup shortcuts.
- §6.10.1: reuse W1's platform `DebouncedPresence` and `PresenceReporter`, without a second debounce. Send coarse presence only, with ACK retry and W1 heartbeat. Start only with a helper-authenticated registration device_id; never guess identity.
- §9.2: five is the total popup budget per wake batch, not concurrent windows. Finishing a dialog does not refill it. The helper supplies wake/backlog metadata; remainder stays in `keyvalet approvals`. Silent delivery can escalate with the same id.
- D10 / §6.9: Escape, close and timeout preserve pending state. Explicit denial is distinct. Windows custom button ids cannot collide with IDCANCEL.

Private agent UI operations: `remote_approval`, `remote_pair`, `remote_confirm_label`, `remote_confirm_global`, `remote_wake`. These are internal agent messages, not new public Appendix C op names. Existing audit/signature/owner checks and trusted subprocess execution remain on real transport paths. macOS invokes AppKit on a subprocess main thread; Windows invokes TaskDialog in the session agent.

## Change requests: Appendix A/C and integration

1. W4 / Appendix C: register the five private UI operations; deliver authenticated request/context, wake boundaries and backlog metadata. Treat deferred as pending and retain the remainder in approvals. Extend the level-only authorization interface to preserve scope/reason. Generic authorization must not render a raw JSON binding.

4. W4 / A.4–A.5 / Appendix C: define a two-phase Strong authentication → typed confirmation → final sign/send operation. The current helper signs/sends in one operation, so a safe preflight gate may cause a second hardware prompt. Never substitute a boolean for a signature.

6. W5/CLI: invoke exposed GrantPlan/DirectivePlan/pairing flows and native dialog adapter from terminal/settings. W6 cannot edit CLI/helper files. No kv-core trait changes are needed.
