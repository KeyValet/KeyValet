Production HPKE composes the existing P-256/HKDF/AES-GCM packages. The reference `hpke` 0.12 KEM API owns serializable private keys and offers static decapsulation; it cannot delegate hardware ECDH directly. Both implementations are checked against the same official RFC 9180 vector, rather than testing one against expectations derived from the other.

## Interpretations recorded before implementation

1. Appendix A.1 overrides the general signature convention: envelope signatures cover AAD concatenated with decoded ciphertext, while inner objects cover JCS of every field except `sig`. Unknown envelope fields are authenticated AAD extensions; `enc` is bound by HPKE decapsulation. See A.1 and §13.2.
2. Appendix A and §13.2 require preserving unknown fields, including nested fields, and preserving the distinction between an absent optional field and explicit `null`. Optional fields use a three-state representation. Closed authorization enums fail parsing; descriptive and future provider enums preserve `Unknown(String)` and validators fail closed for unsupported authority kinds.
3. §6.2 does not give literal JSON keys for `action.kind` or types for empty fields. Canonical input uses `action: {kind}`, a credential reference string, nullable HTTP fields, and a separate agent binding (`repo_or_cwd`, `uid`, `pid`, `exe_sha256`). It cannot be reconstructed from the display-only ApprovalRequest. Host is ASCII lowercased, query keys sorted without deduplication, and path normalization follows RFC 3986 dot-segment removal and unreserved percent decoding without merging slashes or decoding reserved separators.
4. Appendix A.7 does not specify decimal conversion: SAS uses the first six digits of the decimal representation (left-padded to six digits only when shorter) of the unsigned big-endian SHA-256 result. It sorts the identity JWK JCS byte strings; absent approval keys contribute JSON `null`; approval keys come from the approving participant. Two approving participants require an explicit choice of key set.
5. §3.1/Appendix F: compose RFC 9180 from existing P-256/HKDF/AES-GCM libraries because the `hpke` KEM interface requires an owned serializable private key and static decapsulation, which cannot directly call a hardware ECDH provider. `hpke` is a dev dependency for independent interoperability tests. External ECDH returns exactly the 32-byte big-endian P-256 x-coordinate; public points use 65-byte uncompressed SEC1. ES256 signatures use 64-byte IEEE P1363 `r || s`; RS256 uses RSA-2048 PKCS#1 v1.5/SHA-256.
6. Appendix C cannot depend on kv-core because kv-core already depends on kv-ipc. IPC payload types are generic, defaulting to JSON values; kv-core exposes aliases with concrete remote contract types. No dependency cycle or duplicate contract definitions are introduced.
7. Appendix C leaves pair and device params/results abbreviated. Pair start/complete/confirm use PairOffer/PairAccept/PairConfirm; start and complete return SAS, confirm returns an empty object. Device revoke takes `device_id`; rename takes `device_id` and `label`; list returns `devices`. Helper owns peer identity, signing, authorization and state changes.
8. Appendix A.3's `quorum` shape is not specified beyond §13.1. Preserve `sigs` as JSON values; V1 verification rejects non-null quorum and non-device approvers until the team/service workflow defines trust anchors and quorum signature bindings.
9. Appendix A.4 supplements §7.4 with `iss_kind` from §13.2 and optional `confirm`. Grant/Directive unsigned IPC inputs omit `sig`. Verification rejects unsupported issuer kinds and algorithm claims differing from the trusted device record.
10. §7.5 does not include a Directive key level. Verification takes authenticated signing level from the caller, trying only the corresponding recorded approval key; it never accepts a DK as an approval key. For state-sensitive ops, caller supplies current state. Unknown state or unsupported directives cannot authorize a change.
11. §6.10.1 places PresenceProbe in kv-platform, but W0 is authorized to modify kv-core/kv-ipc only. Define the shared presence state and trait in kv-ipc and re-export them from kv-core::remote; kv-platform already depends on kv-ipc. DeviceKeyProvider also gets an IPC-level hardware interface (public JWK as lossless JSON, sanitized DeviceKeyError, descriptive kind strings), with a blanket core adapter to the typed W0 interface. This resolves the kv-core → kv-platform cycle without changing either dependency edge.

12. Appendix A.1 / product §J-R8: unknown envelope types are retained, acknowledged by the helper, and rejected for processing. Envelope version must equal 1; v=0 also fails closed. The strict JSON entrypoint rejects duplicate object keys and malformed Unicode; integer inputs outside ±(2^53−1) are rejected to prevent cross-runtime signing disagreement. Floating point uses RFC 8785 number serialization.
13. §6.2: empty HTTP/credential bindings are explicit null and sorted query keys retain duplicates. Normalization decodes percent-encoded unreserved bytes before removing dot segments; reserved escapes are uppercase. It does not normalize Unicode.
14. §6.10.1: PresenceSignals exposes every raw session, lock/screen-saver, idle, display, remote-session and approval-channel signal as nullable values, plus unknown platform-specific signal fields. PresenceProbe has no implementation in W0.

17. Appendix A preamble / A.7: “AK_s signs sas” does not specify a byte encoding. Apply the general object-wide JCS convention to PairConfirm (`{sas, ...unknown fields}` excluding sig) so every unknown field participates in verification, as explicitly required by W0. Confirm does not sign bare ASCII digits.
18. Build scope: enabling tokio/macros in kv-core normal dependencies is required for the existing kv-platform tokio::select! calls when building these packages alone. W9 should declare macros in kv-platform itself.

19. §7.5 / A.5: set_device_label is Strong because it modifies the trusted device directory (§3.2); notify is Quick because it only affects delivery (§6.10.6). Creating a batch class or changing its match is Strong; shortening an existing identical-match class is Quick. unlock TTL is bounded to 1–86400 seconds; class expiration to 1–86400 seconds.
20. Appendix A.3: quorum is optional and nullable (shown null, described optional in §13.1); reason is optional and nullable for lossless signing. Appendix A.8 fields are status-dependent and optional; result is valid only for status=ok. DeviceRecord ak_q/ak_s/attestation and Grant exp are required nullable fields.

22. Appendix A.1 / §3.4: device_revoke is an identity-authenticated notification, never standalone permission to revoke a device; helper authorization requires the signed revoke_device Directive and the Strong confirmation flow.

25.
