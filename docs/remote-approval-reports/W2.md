## Implementation

The relay directly imports W0's `Envelope`, `DeviceRecord`, Appendix B request/response objects, strict JSON parser and signature verifiers. Ciphertext is decoded by the W0 outer-signature verifier as opaque bytes; production code never calls HPKE open, parses ciphertext plaintext, or holds an encryption/signing private key. Unknown signed envelope fields survive transport and storage. Future envelope versions remain deliverable through `/v1/messages` for receiver-side ack; the V1 approval state machine accepts V1 approval envelopes.

SQLite uses WAL on disk, foreign keys, secure deletion and transactions. The six Appendix §8.3 tables are present. Extra columns preserve complete W0 records, push tokens, pairing identifiers/confirmation flags and a hash of the confirmed SAS. `used_pair_tokens` retains hash-only replay tombstones through expiry plus seven days; completed/expired pairings clear their active token hash. Device revocation is a timestamped tombstone. Challenges, connection presence and sliding rate windows live in memory. `plan` defaults to `self_hosted`; there is no billing or plan quota execution.

Every standalone registration creates an anonymous account and returns that account's recovery code once. Codes have 256 bits of randomness and are stored only as Argon2id PHC hashes (Argon2 defaults: version 19, m=19456 KiB, t=2, p=1). Challenges are random 32-byte values valid for 60 seconds, single-use after successful ES256 verification. Sessions are random opaque tokens, stored by SHA-256 hash, valid for 24 hours; a new signed challenge renews access.

Pair completion registers a new joiner into the initiator's account without issuing another recovery code. An already registered singleton can migrate only with its own authenticated DK session and an exact matching device record; old sessions and its old recovery hash are invalidated. Pending joiners can authenticate and finish pairing, but can only exchange pairing ciphertext with their exact partner until both confirmations succeed. A Strong participant's SAS confirmation is verified with its AK_s; an execute-only participant submits the empty-signature terminal confirmation from A.7. The relay compares SAS hashes and never retains the raw pairing token. A valid SAS mismatch permanently aborts the pairing, clears its active token hash, revokes the pending joiner and invalidates its sessions; the same pairing cannot be used to guess another SAS.

Fan-out inserts one ciphertext row for each recipient. Signature checks, recipient membership and first-reply resolution run in one transaction. Only an original recipient can reply to the requester; the first valid outer-signed reply marks `resolved`, without learning allow/deny. Invalid and replayed replies do not resolve. Cancellation and expiry notify the remaining devices. Waiting pulls return only the caller's `to` rows, including still-waiting requests already acknowledged. Non-approval ciphertext and replies replay on reconnect until recipient-specific ack. An ack from another recipient cannot affect those rows.

Durable acceptance determines the submission response. A failed best-effort delivery timestamp update cannot return a submission error after the envelope or resolution has committed. Strong revocation verifies its proof and commits the mutation in one critical section; its challenge is consumed only after success. Recovery verification runs outside that section and rechecks authentication, target membership and pairing readiness before mutation.

Cleanup runs every 30 seconds. Non-request rows are removed seven days after ack; approval rows and their request/escalation ciphertext remain until expiry plus seven days. An unacknowledged non-approval message is retained, even after envelope expiry, as required by the persist-until-ack contract; expired ciphertext is not delivered. Expired pending joiners are revoked. Expired sessions and challenges are removed.

Limits use sliding 60-second windows: 60 approval submissions per device; 600 message envelopes/replies per device; at most 500 account-wide pending approvals plus unacknowledged, unexpired non-request messages; each serialized envelope at most 80 KiB; HTTP/WS input at most 1 MiB. Invalid attempts can consume the sender's rate budget. Additional abuse limits are 10 registrations/IP/min, 60 auth calls/IP/min, 60 pair completions/IP/min, 10 pair starts/device/min, 10 outstanding pairings/account, 10 revocations/IP/min, 60 WS upgrades/IP/min and 10 upgrades/device/min. `Retry-After: 60` accompanies HTTP 429. `CF-Connecting-IP` is trusted only for the exact socket peer `127.0.0.1`; invalid/multiple IP headers fall back to the socket address. IPv6 loopback and other 127/8 addresses are not trusted proxies.

WebSockets require `kv-relay-v1`. Application ping returns pong; envelope submission returns ack; incoming ack updates only that recipient's durable inbox. A bounded presence queue disconnects slow consumers so they can replay from SQLite. Server control pings every 30 seconds keep nginx's 90-second read timer active. Lack of inbound application/control activity for 100 seconds closes the connection, including a client that never answers server pings. Session expiry/revocation closes presence. Replaced connections cannot erase their replacement's presence entry. A failed reconnect preserves the previous connection. Replacing a socket leaves a live authentication challenge usable; revocation and migration explicitly invalidate it. Shutdown interrupts the initial inbox replay even if its next write is stalled.

## Authorized extensions and W0 change requests

The user explicitly authorized temporary relay metadata control frames and extra Strong-proof headers. No kv-core files were changed.

1. **W0: add distinct relay-control WS variants.** The implemented shapes are `{"t":"pair_accept","pairing_id":"ULID","joiner":DeviceRecord}` and `{"t":"approval_cancel","id":"ULID"}`. They are relay-originated metadata notifications, not forged E2E Envelopes. The relay has neither a device DK nor a recipient encryption key, and cannot manufacture the signed cancellation/pair-accept Envelope implied by the frozen prose. Pair acceptance replays to the initiator while the pairing remains accepted. Approval queue state suppresses obsolete requests on reconnect. Clients must treat these notifications as untrusted delivery/control hints; they cannot authorize execution or replace signed SAS/decision verification. Ordinary device-signed pair_* and other Envelopes still use the frozen envelope frame.
2. **W0: type `PairCompleteResponse.account_id`.** It is currently an additive field preserved by W0's `extra` map and accepted by its schema. The joiner needs the routing account before it can construct its first envelope. The frozen two-field response has no way to provide it. Existing fields keep their frozen shapes.
3. **W0: define Strong proof for device deletion.** For `by=device`, first fetch `/v1/auth/challenge` for the caller, then send `X-KV-Challenge` and `X-KV-Strong-Signature`. The signature is AK_s (its recorded ES256/RS256 algorithm) over JCS of `{"action":"revoke_device","account":"acct_...","by":"caller-device","device_id":"target-device","challenge":"b64url"}`. The relay requires approve_strong capability, a valid caller session, same account, a live unused challenge and the valid signature. It consumes the challenge atomically with revocation. A DK session or declared Strong capability alone never authorizes this action.
4. **W0: specify registered-joiner migration.** New joiners need no session for complete. Existing joiners must provide their own session, must be the only device in their prior account, and must have no prior pairing/message/approval history. This avoids moving another account based on possession of a pairing token and a copied public record.
5. **Lost-all-devices recovery is implemented separately.** `POST /v1/recovery` uses a recovery code and replacement DK proof without an old Device session. It atomically revokes old devices/sessions, cancels pending routing state, registers the replacement and rotates the code. The existing authenticated DELETE route retains its contract. See [recovery and audit](../remote-recovery-audit.zh-CN.md) for the client API and remaining rollback boundaries.
6. **W9: use distinct server/client service names.** Both workflows provide an asset named keyvalet-relay.service. The W2 checklist installs the relay-server asset as `keyvalet-relay-server.service`, with dedicated `keyvalet-relay-server` user/group, leaving the relay-client's unit name available.

## Harness usage

Add `kv-server = { path = "../kv-server" }` to the consuming crate's dev-dependencies and run inside a Tokio runtime:

```rust
#[tokio::test]
async fn relay_health() {
    let (base, relay) = kv_server::spawn_test_relay();
    let response = reqwest::get(base.join("v1/health").unwrap()).await.unwrap();
    assert!(response.status().is_success());
    relay.advance_time(std::time::Duration::from_secs(7 * 86400 + 601));
    let _stats = relay.cleanup();
    relay.shutdown().await;
}
```

The exact requested synchronous API is `pub fn spawn_test_relay() -> (Url, Handle)`. It uses in-memory SQLite and an ephemeral 127.0.0.1 port. `Handle::shutdown().await` closes the server and worker; dropping the handle also signals shutdown. `advance_time` advances application expiry only, not the WebSocket monotonic heartbeat clock. `cleanup`, `logs`, and read-only `inspect` support deterministic integration assertions. `spawn_test_relay_with_data(path)` provides a WAL database for disk/restart assertions. Harness inspection is a test-only caller capability, not an HTTP debugging endpoint.

## Review and coverage follow-up

The follow-up review covered authentication and recovery, pairing membership and SAS confirmations, approval state transitions, fan-out and acknowledgments, queue and rate boundaries, SQLite transactions and cleanup, WebSocket connection lifecycle, CLI startup/shutdown, and the deployment templates. Six behavior defects were fixed:

1. A valid SAS mismatch previously left an accepted pairing retryable. It now permanently aborts the pairing and revokes the pending membership. Invalid signatures do not consume the legitimate participant's attempt.
2. Revoking a requester cancelled its waiting approvals without notifying recipients. The transaction now collects cancellation notifications and emits them only after a successful commit.
3. Duplicate `CF-Connecting-IP` header entries previously used the first value. Ambiguous, malformed or missing values now fall back to the socket peer; only the exact IPv4 loopback proxy is trusted.
4. Reconnect inserted presence before reading and parsing its durable inbox. A storage/read failure could leave a stale online entry and replace a working connection. Frames are now prepared before changing presence.
5. Replacing presence inadvertently consumed an unused authentication challenge. Socket replacement now preserves the challenge; revocation and account migration invalidate it explicitly.
6. Shutdown was not observed during initial inbox replay. It now interrupts a stalled replay immediately, with shutdown taking priority over another write.

The tests also verify that W0 rejects all standard JWK private-key members in DK/AK public records, that failed registration/revocation/message/ack transactions preserve prior state, that Strong proof and pending membership fail closed, and that storage/panic errors cannot enter relay logs or API bodies. WebSocket transport and OS-signal waiting have internal boundaries for deterministic failure injection. Production and tests use the same protocol and timeout implementation; no production branch is compiled out for coverage. The actual socket, real 30/100-second heartbeat, CLI signal handling and ciphertext-only disk tests are retained.

The second review fixed two further behavior defects:

1. A failed `delivered_at` update could return an error after a successful message/approval/reply commit and live delivery. This now preserves the accepted response. Regression tests force tracking failures, verify ciphertext persistence and delivery, and verify that replay remains rejected.
2. Strong revocation consumed its one-use challenge before its SQL transaction completed and rechecked immutable proof headers in a second critical section. Proof verification and mutation now share a critical section, and a failed transaction preserves the challenge for a legitimate retry. Tests fail the transaction, retry the same proof successfully, then verify that the committed proof is consumed.

The new tests run 1,588 SQLite preparation/execution scenarios across 19 operations, using the real SQLite authorizer and query progress hooks with copied in-memory databases. They verify complete rollback of failed mutations and preserve the old presence connection on failed reconnect. Other tests cover binding size/count errors, each decoded column in corrupt rows, malformed persisted wire records, password worker failures/panics, session/account/readiness changes during password verification, independent auth/pairing/reply rate limits, permissions, startup/shutdown, and stalled heartbeat writes. The progress hook interrupts queries; write/commit failures are denied during preparation, since a progress callback can run after an autocommit write has already committed.

Query collection now shares one sanitized storage boundary. Derived wire records contain only primitive JSON fields and JSON values, so byte serialization uses an explicit infallibility assertion; canonical JCS validation remains fallible and is tested with unsafe integers. Password work and permission application have private injectable boundaries, while normal execution uses Argon2id and the actual filesystem. No production code is excluded from coverage. No new registry dependency/version was added in this second review: only the existing rusqlite 0.32.1 `backup`, `hooks`, and `limits` features were enabled for tests.
