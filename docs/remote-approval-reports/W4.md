# W4：执行端远程审批核心

## 状态与边界

原 W4 实现只修改 `rust/crates/kv-helper/`；用户另授权本报告、必要依赖和 `rust/Cargo.lock`。随后用户要求 W1–W5 整体接口验收并直接修复问题，追加了跨工作流接口修复及回归测试。没有执行 commit、branch、stash、checkout、reset、rebase 或 push 等改变 Git 状态的命令。共享工作树内保留了其他工作流的修改。

W4 提供可注入、可测试的执行端授权后端和真实 IPC 进程身份适配器。`RemoteHelper::new(Store, DeviceRecord, account, ApprovalConfig, Services)` 是唯一密钥、在场探针、vault 目录镜像、审计和执行 runner 注入点。W0 的 SoftwareDeviceKey 仅用于测试和随机数熵源，不作为硬件密钥失败时的认证替代品。

**生产 bootstrap 尚待跨 crate 接口交付**：当前 daemon 没有创建并安装已验证的 RemoteHelper；未安装时所有允许的 remote.* 操作返回 `remote_unavailable`，越权操作仍返回 `forbidden`。既有凭证 dispatch 仍使用原有 kv-core 授权管线。不能把本报告理解成远程审批已在已安装产品上启用；后面的变更请求是接入条件。

## 状态与验证位置

`store::PendingState` 定义 waiting / approved / approved_unused / executed / denied / expired / cancelled。`engine::accept_decision` 在 SQLite 事务中提交决定、nonce、派生授权与审计；`execute_approved` 在真实执行前领取，按设备吊销、授权 epoch、真实 agent 是否存活和完整请求 hash 再检查。领取后的执行不盲目重试，结果也只能领取一次。

§6.5 顺序严格为：

1. `engine::receive`：版本、接收方、account、配对/吊销信任、DK 信封验签与 HPKE/时间验证。
2. `accept_decision`：pending 存在且 waiting。
3. 决定 digest/nonce 与完整规范化快照、快照 kind/requester/exp 对应。
4. level 达到最低要求；T2、unlock/admin、standing 强制 Strong。
5. 按 level 选择设备记录的 AK 与 alg 验签，拒绝 service/org/quorum 和错误 approver。
6. `Store::consume_nonce`：INSERT OR FAIL；nonce 与状态修改同一事务。
7. W0 offered-scope 验证、拒绝或批准；写 Grant/unlock lease，选择 approved 或 approved_unused。
8. 写执行端审计，通知其余审批端取消；提交后执行。审批端签发 ledger 与审计在 `ipc::issue_decision`。

验证失败立即停止，固定 reason 写审计，不输出 SQL 参数、密文、凭证或完整请求。审计不可用则不能授予或执行授权。完整请求是 `FullRequest` 的 Zeroizing 内存对象，单个上限 1 MiB，既不序列化到 pending 表也不写 outbox；过期、取消和后台存储故障均清理。执行结果也在过期/领取/后端丢弃时 scrub。

§7.5 位于 `directives::apply_directive_locked`：AK 验签 → 操作档位/二次确认 → 原子 nonce → exp → 执行 → 审计/结果。原始签名对象与未知扩展字段均按 W0 JCS 保留。

§6.9 位于 `config` 的预算函数、`engine::{wait,retry,result_locked}`、`pipeline::{run,wait_http}`、`ipc` 的 PendingForAgent/PendingStopBlock：调用内 min(config, runtime−10)，续等 min(max_wait, tool/config, runtime−10)，HTTP min(config, hint−60)，未知 HTTP 55 秒；relay offline 提前放手；重发比较除 nonce/exp 外全部规范化字段及完整执行 hash。

## 复查修复

- 原始决定派生的 Grant 重新构造后与保存的全部字段比较，并比对原 pending/request/canonical/decision，防止篡改 scope、寿命或 session。
- 合并 per_use 临时票只覆盖完整原执行绑定，不能用同凭证的批准 A 执行 B。
- 执行前再次检查 issuer 吊销与 epoch；等待前先检查调用方归属。
- 已验证 DirectiveResult 只能接收一次，ID 必须与信封一致，不能覆盖首次结果。
- Pair SAS 查询只通过已认证 CliOwner status 返回；终端 y 与对方 AK_s 签名缺一不可。
- 请求创建和 Grant 覆盖的错误统一拒绝并审计；后台数据库失败清理内存请求，不能延长保留时间。
- SQLite 故障注入发现 Directive 提交后还执行了可能失败的 SQL 清理查询；现将这些查询放在提交前，提交后只做内存清理。
- session 结束的取消、session Grant 吊销与 unlock lease 清除统一事务。
- 到期必须投递 `approval_cancel`；取消通知使用自己的 60 秒有效期，不能以已到期请求的 exp 封顶，否则定时清理会在投递前删掉它。接收方只关闭提示，取消信封不产生批准权限。
- Lock 与 cancel_approval 复用 `cancel_in_transaction`，逐审批记录 `approval_cancelled`，在事务提交后清理请求内存；不改写已执行的审批。
- Store 审计不可用时，独立 AuditSink 收到固定元数据的 `remote_audit_rejected`；该补偿记录不会使原操作成功。通知查询失败也记录拒绝原因。
- 通知和 Stop 查询共用 `Store::pending_ids_for_agent`，再检查规范化快照里的 uid/pid；通知不消费结果、跳过已领取及丢失结果的执行记录。
- 重复请求只可完全相同；有已签决定的 inbound request 不得重新弹出。PairAccept 的 HPKE 失败会清掉配对内存，不写目录。

## 有意偏差与原因

- §16.7 的三个不同操作、同凭证合并，目前仅合并 session 内 30 秒内**完整执行绑定相同**的 T0/T1 use；不同操作各自 pending，T2 永不合并。W0 单一 canonical/digest 不能承诺任意多个请求，直接合并会形成“批 A 执行 B”。等待 W4-CR-08 的签名批对象。
- 二次批准的 live 状态已不是 waiting，依 §6.5 第 2 步返回 not_waiting，而不会越过第 2 步到 nonce 检查。W0 replay 向量用 waiting + 已消费 nonce 验证第 6 步 replay。
- §6.6 的旧“T2 永不被 Grant 覆盖”与 §7.4/7.6 的明确新规则矛盾；采用后者及 W0 类型/向量：只有明确 max_tier=T2 的票覆盖，强制 unattended_t2 审计。
- 弹窗派生票保存原 ApprovalDecision 签名证明，不能伪造审批设备对 Grant 的新 AK 签名。它仅为 helper 内部授权，重新验证签名及原快照；跨设备转发必须是审批端独立签发的 Grant。
- Grant 安装按 W0 向量验收；helper 签发所有 T2 settings Grant 都要求 Strong 和目标 label 二次确认。W0 有限期 T2 接收验证缺确认限制，需 CR-09 统一。
- budget 周期以 nbf 锚定 hour/day/week 窗口；每张命中票独立扣 calls/bytes，tier 取最小。status 对已安装有效 T2 票保留无人值守标识，即便当前预算耗尽（预算可以随后重置）。
- Relay 掉线密文仍保留；现通过追加的 durable receipt 精确移交/退休，拉取本身不删除。body 丢失后返回 approved_retry_required；领取 executed 后崩溃保持 at-most-once，不盲目重新执行。
